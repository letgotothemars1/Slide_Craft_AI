**Owner:** Developer B. **Difficulty:** 5/5. **Budget:** 3–4 days. **Depends on:** approved outline from M03. **Status:** ready after M03 API. **Branch:** `mvp/M04-progressive-build`.

**Outcome:** five slides become ready one by one and a single text block can be regenerated without destroying accepted work.

**Do:** on `POST /projects/{id}/build`, queue a background loop over approved outline items. For each item, mark slide `generating`, call the selected LLM for one validated slide spec using the approved thesis/order, assignment constraints, theme, relevant page-aware excerpts, and short summaries of neighboring slides; persist that slide as `ready` before starting the next. Expose state through `GET /projects/{id}` so UI polling can display real progress. Add one block-regeneration endpoint for `title` or `body`. Lock only the target block; check its revision before saving the model result and discard stale output if a newer edit exists. Failed slides show `error` and can retry independently.

**Likely files:** new `app/services/modular_*`, `app/routers/projects.py`, `app/repository.py`, `app/schemas.py`. Reuse provider selection in `app/services/llm_service.py` but avoid a broad rewrite. Existing `orchestrator.py` is whole-deck and should continue to power old `/generate`.

**Done when:** API polling observes slide 1 `ready` while slide 5 is still `queued`; editing slide 1 body survives generation of later slides; regenerating slide 1 title leaves body and slide 2 untouched; a deliberately stale result cannot overwrite a newer edit; retrying one error does not restart the deck. Use deterministic fake-model responses for these checks, then test once with the chosen real provider.
